# OTPProvider

How a sign-in code reaches somebody's phone. Identity is the phone number (D-010), so this port is
the front door: whatever implements it decides whether the person typing a code actually holds the
number.

Interface: `apps/backend/src/letmehandle/domain/ports/otp.py`
Contract suite: `OTPProviderContract` in `apps/backend/tests/contracts/other_ports.py`
Implementations:

| Provider | Chosen by | Who owns the code | For production |
| --- | --- | --- | --- |
| `adapters/otp/mock.py` | `OTP_PROVIDER=mock` | the application; fixed at `123456` | no — refuses to start there |
| `adapters/otp/twilio_sms.py` | `OTP_PROVIDER=twilio_sms` | the application (D-037) | yes |
| `adapters/otp/twilio_verify.py` | `OTP_PROVIDER=twilio_verify` | the provider's verification service (D-042) | yes |
| `adapters/otp/by_calling_code.py` | `OTP_PROVIDER_BY_CALLING_CODE` | whichever provider serves the number | only if every provider is |

Two providers deliver real codes to real handsets. A deployment exposed to anybody but its
developers runs with one of them and `APP_ENV=production`; the mock refuses to start there.

## The interface

| Member | Means |
| --- | --- |
| `name` | For logs and readiness, never for a decision |
| `is_safe_for_production` | Whether it actually delivers to a real handset |
| `fixed_code` | A code every challenge uses instead of a random one, or `None`. Only a provider that is not safe for production may offer one; the authentication service refuses it from any other |
| `send(number, code)` | Deliver a code the application made, or raise `UnreachableNumberError` or `ProviderError` |
| `issues_its_own_codes(number)` | Whether this provider, not the application, makes and checks `number`'s code. False unless the provider says otherwise |
| `send_own_code(number)` | Make a code and deliver it, raising what `send` raises. Only where `issues_its_own_codes` is true |
| `check(number, code)` | Whether the code is the one sent and still unused: `False` for wrong, expired, used or never sent; `ProviderError` when the provider cannot say. Only where `issues_its_own_codes` is true |

The code is normally generated by the application, so its length, alphabet and expiry are the
product's decisions and a provider only carries it (D-037). Where a country's operators deliver only
the provider's own registered message, the provider makes the code and checks it (D-042). Either
way the attempt limits, the expiry, single use and every sending limit are the authentication
service's: it asks a provider to check only a challenge that is still open, counts a wrong answer
as an attempt, and treats a provider that cannot answer as unavailable, never as a right code.

## Text messages

`SmsOTPProvider` sends the application's code in one text message from `SMS_FROM_NUMBER` through
the telephony provider's Messaging API. A number it will not deliver to is `UnreachableNumberError`
(`422 number_unreachable`); any other failure is a `ProviderError` (`503 provider_unavailable`),
and a request sent but never answered is counted as if delivered.

## The verification service

`VerifyOTPProvider` asks the provider's verification service to make a code and text it in the
service's own registered message, and later asks the service whether a code is right. It needs no
sender number. Requests and what they become:

| Request | Answer | Becomes |
| --- | --- | --- |
| start (`To`, `Channel=sms`) | 201 | sent |
| start | 400 with 60200, 21211, 21614 or 60205 | `UnreachableNumberError` |
| start or check | 429, 5xx, connection refused | `ProviderError`, retryable |
| start or check | timed out after sending | `DeliveryUncertainError` |
| check (`To`, `Code`) | 200 `approved` | right |
| check | 200 any other status | wrong |
| check | 404, or 429 with 60202 | wrong: expired, used, never sent, or out of guesses |

The service keeps its own count of checks and its own expiry. The application's are stated and
tighter, so the service's only ever refuses sooner. Starting a second verification while one is
pending resends the same code; only the application's latest challenge accepts it.

## The mock

`MockOTPProvider` records the code instead of sending it and logs it with the number masked. It
offers the fixed development code `123456`, so anybody running the project can sign in without
reading a log, and a development build of the app says so on the code screen. It raises at
construction when the deployment is production, which stops the process at startup: the failure it
prevents is silent and total — everybody could sign in as anybody.

## Configuration

| Variable | Meaning |
| --- | --- |
| `OTP_PROVIDER` | Which provider delivers codes: `mock`, `twilio_sms` or `twilio_verify` |
| `SMS_ACCOUNT_ID`, `SMS_AUTH_TOKEN` | The account either real provider uses |
| `SMS_FROM_NUMBER` | The number `twilio_sms` texts from |
| `SMS_VERIFY_SERVICE_ID` | The verification service `twilio_verify` uses |

Startup refuses a chosen provider missing any of its variables, naming them and never a value.

## A provider per country

`OTP_PROVIDER_BY_CALLING_CODE=91:twilio_verify` sends codes for numbers with that calling code
through that provider, and every other number's through `OTP_PROVIDER` (D-041). Bootstrap builds each
named provider once and puts `OTPProviderByCallingCode` (`adapters/otp/by_calling_code.py`) in front
of them. It routes sending, `issues_its_own_codes` and checking by the same calling code, so a code is
always checked by the provider that sent it. It is safe for production only if every provider is,
and fixes a testing code only when every provider fixes the same one. A calling code not in
`OTP_ALLOWED_CALLING_CODES` is refused at startup.

India, with texts for everybody else:

```bash
OTP_PROVIDER=twilio_sms
OTP_PROVIDER_BY_CALLING_CODE=91:twilio_verify
OTP_ALLOWED_CALLING_CODES=1,91
SMS_ACCOUNT_ID=
SMS_AUTH_TOKEN=
SMS_FROM_NUMBER=
SMS_VERIFY_SERVICE_ID=
```

## Adding one

A worked example: an SMS provider that sends through an HTTP API.

1. **The adapter**, in `adapters/otp/sms/provider.py`. Every vendor type and exception stays inside
   it:

   ```python
   class SmsOTPProvider(OTPProvider):
       """Sends a code as a text message through the provider's HTTP API."""

       def __init__(self, *, client: httpx.AsyncClient, sender: PhoneNumber) -> None:
           self._client = client
           self._sender = sender

       @property
       def name(self) -> str:
           return "sms"

       @property
       def is_safe_for_production(self) -> bool:
           return True

       async def send(self, number: PhoneNumber, code: str) -> None:
           try:
               response = await self._client.post(
                   "/messages",
                   json={"from": self._sender.value, "to": number.value, "body": code},
               )
               response.raise_for_status()
           except httpx.HTTPError as error:
               # The number is never in the message: errors are logged and pasted into issues.
               raise ProviderError(self.name, type(error).__name__, retryable=True) from None
   ```

   It does not override `fixed_code`: a provider that delivers must never make every code a
   constant. A provider that can only send a code it makes overrides `issues_its_own_codes`,
   `send_own_code` and `check` instead, and raises `CapabilityNotSupportedError` from `send`; see
   `adapters/otp/twilio_verify.py`.

2. **The contract**, in `apps/backend/tests/contracts/test_sms_otp_contract.py`, against a simulated
   API rather than the real one:

   ```python
   class TestSmsOTPProvider(OTPProviderContract):
       @pytest.fixture
       def otp(self) -> SmsOTPProvider:
           return SmsOTPProvider(client=simulated_sms_client(), sender=A_SENDER)
   ```

   Add tests of your own beside the contract for what only this provider does: a refused request
   becomes `ProviderError`, and nothing it raises or logs carries the number or the code.

3. **The settings.** Add `SMS = "sms"` to `OTPProviderName`, and the provider's own variables to
   `Settings` with a `description` and `required_when`. Add them to `.env.example` and to the
   backend's environment in `docker-compose.yml`, then run `make config-reference`.
   `make verify` fails until all four agree.

4. **The choice.** Add a case to `_otp_provider_named` in `bootstrap.py`. The match is exhaustive,
   so a member without a case fails type checking rather than falling through to the mock.

5. **The docs.** Update the implementations line and the configuration table on this page.

Nothing in `domain/`, `application/` or `api/` changes. Sign-in, rate limits and the production
guard already work through the port.
